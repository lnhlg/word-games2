# 0002 · 角色状态：会话级、AI 主持、每次变化带依据

- 日期：2026-11-13
- 状态：已采纳

## 背景

群像剧场的长剧里，角色「此刻的处境」会漂：中毒没中毒、被谁怀疑、对谁的好感到了哪一步。这些信息不在角色卡里（卡是固定人设），也不在 prompt 的最近八回合里（读一遍才知道，而且越写越稀释）。导演提出：一场戏里能给角色自定义若干状态值，最好还能通过跟 AI 对话把「该看哪些状态项」定出来。

这条需求同时踩到三条旧线：酒馆 V2 卡是无损导入的（不能随便加私有字段）、旧的互动小说机制带过 `state.json`（已整体下线，测试明确断言新建会话不产生它）、`messages.jsonl` 是可原地改写的长期资产（新增字段必须可选）。

## 决策

1. **状态属于一场戏，不进角色卡。** `session.json` 新增可选字段 `statusTemplate`；角色卡的 `extensions` 一个字节都不动。
2. **模板与值分两层。** 状态模板（`StatusTemplate`）回答「看哪些维度」，只有名称与可选说明；状态值（`StatusValue`）回答「此刻是多少」。
3. **模板进 `session.json`，值变更流进 `<session>/status.jsonl`。** 模板是与 `cast` / `perspective` 同级的元数据；值是随时间演进的事实，追加式记录，当前值由重放得出。
4. **每回合一次合并调用。** 正文写完后，与「后续剧情选项」共用同一次轻量调用；模型输出 3 条选项 + 状态变化。JSON 解析按字段降级：能读出哪个字段就应用哪个，两者都坏就当没生成，绝不影响正文。
5. **模型给绝对值，不给增量；每次变化必须带一句依据。** 面板显示成 `好感度 30 → 35（她替他挡了一刀）`。
6. **AI 可改值、可提议新增条目，不能删除条目。** 每角色上限 8 条，超限的新增提议直接丢弃。
7. **状态跟回合走。** 删除最后一回合回滚到该回合之前；重新生成最后一回合先丢弃该回合的状态记录再重算；编辑任意回合不重算，只把该回合的依据标记为过期。
8. **注入位置是演员表里该角色段的末尾**（`当前状态：好感度 35；被沈砚怀疑`）；**剧场契约**新增一条：状态是处境，正文里不要直接报出条目名或数值。

## 理由

- **会话级而不是卡级**：状态是这一场戏的处境，不是人物的固有属性。写进卡会让同一张卡在两场戏里打架，一改状态就动 V2 文件，与「导入零损耗」的承诺手感冲突。将来若要跨戏复用，会话里的模板本来就是独立清单，加一个「来源」字段就能从卡上复制，不推翻形状。
- **模板与值分开**：导演要的是「这个角色该看哪些维度」，这是设计决策；模型每回合要改的是「这些维度现在是多少」，这是叙述事实。混在一起，AI 一改值就等于改设计。
- **合并调用而不是第三次调用**：选项调用本来就在正文之后跑一次，输入里已经有最近一段情节；多塞一份状态清单只增加几十个 token，却省掉一次完整往返。合并的代价是两个功能共享一次失败，所以解析必须按字段降级。
- **绝对值而不是增量**：条目没有类型系统，`+5` 没法可靠地解析原值；而模型算加法本来就不稳。绝对值由程序 diff 出方向，`30 → 35` 是算出来的，不是模型说的。
- **带依据**：状态写错会污染后面所有回合的 prompt，而它不像正文那样一读就知道错。一句依据让导演扫一眼就能判断，比每回合弹确认轻得多。
- **AI 不能删条目**：删是设计决策。让模型顺手删，面板会无声地漂移。
- **回滚只覆盖尾巴**：删除与重新生成本来就只允许最后一回合（见 ADR 0001），所以「回滚」永远是丢弃尾部记录，不需要重算中间任何一段。

## 后果

- 正面：导演可以给每个角色定几个维度，让 AI 每回合维护，并且随时手改；状态在界面上与角色卡放在一起，边读正文边能看到谁变了、为什么变。
- 负面：每回合多一份状态清单进 prompt（每角色最多 8 条）；合并调用一旦整体失败，本回合既没有选项也没有状态更新（正文不受影响）；编辑任意回合后状态依据会与原文脱节，只能提示、不能自动重算。

## 被否决的方案

- **状态写进角色卡 `extensions`**：卡级唯一会让「这场想加个伤势」污染所有戏；且状态值跨戏共享会互相干扰。
- **状态存进 `messages.jsonl` 的 `narrative` 记录**（像 `nextOptions` 那样与情节同生共死）：导演手动改一格不属于任何回合，没有地方安放；而且每读一次会话都要扫全部消息才能得出当前值。
- **每回合弹确认再生效**：打断写作流；导演多半会忽略确认，「不点等于不更新」又退化成手动维护。
- **独立的第三次调用**：多一次往返与一次失败面，换不来独立性——合并调用的失败本来就不影响正文。
- **让模型在正文末尾附带状态块再剥离**：直接违反剧场契约「只输出小说正文」，而且各模型格式稳定性差。
- **模型输出增量（`+5`）**：条目没有类型，增量无法可靠解析；加法由模型算也容易错。
- **卡的 `extensions` 存状态模板 + 会话存值（双层）**：多一套「卡上那份过时了」的同步问题，v1 不值得。
